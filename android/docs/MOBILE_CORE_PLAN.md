# Mobile Blocknet Core: implementation plan

Status: **mobile candidate tested on an isolated S22 sidecar; battery measurement pending**. Ordered Core patches 0001–0009 and the Android mobile build implement a no-listener peer profile and graceful foreground-only stop/restart. Foreground-only is the default when no preference exists; an explicit continuous-sync choice remains available, and manual Stop is definitive. A true in-process suspend is not implemented, and no battery saving has been measured on a synced phone. The pinned Core commit is `5a37ed52f0426951eaac2f0ae86bf0bb6d70a83e`; verify each signed artifact's provenance.

The mobile profile declines chain-data and peer-list requests, including streams opened over connections initiated by the phone. It still handles sync status and incoming blocks, fetches its own chain data, and retains incoming Dandelion/transaction handlers to preserve stem forwarding behavior. Thus “client-only” here does not mean zero transaction relay or idle peer traffic. The foreground-only stop/restart path stops Core in the background, which can impose a full-chain ring-index rebuild on return; its energy and latency costs require device measurement. An explicitly selected continuous mode keeps loaded wallet secrets in a resident Core process despite the API lock.

## Decision

Keep Core as a separate, app-owned **ARM64 PIE executable** and build a mobile variant from the pinned Core commit plus small, reviewed patches. Preserve Core's consensus, wallet file format, local scanner (`wallet/scanner.go:100-157`), canonical-chain ring-member selection (`api_handlers.go:3177-3184`, `block.go:2769-2865`), signing, and Dandelion++ transaction broadcast (`daemon.go:1309-1325`). The Java app remains the UI, network-policy owner, and authenticated loopback API client. Do not embed wallet or P2P components in the first mobile iteration.

The existing pipeline already cross-builds an experimental Core and packages it as `lib/arm64-v8a/libblocknet_core.so` (an executable despite its package suffix): [`build-core-android.sh`](../scripts/build-core-android.sh), [`app/build.gradle`](../app/build.gradle), and [Android CI](../../.github/workflows/android.yml). It also builds a separate read-only offline wallet helper from the same Core revision with [`build-offline-wallet-view.sh`](../scripts/build-offline-wallet-view.sh). Reuse those boundaries. Do not substitute the supplied binary silently or claim to reproduce it byte for byte: its recorded source was dirty and its exact changes are unavailable (see [patch provenance](../core-patches/README.md)).

| Option | Benefit | Cost and decision |
| --- | --- | --- |
| Patched Core executable | Retains the tested Go/Rust wallet and consensus implementation, isolated process, existing loopback API, storage, packaging, and CI provenance. | Requires a carefully tested lifecycle and peer-policy patch. **Choose this first.** |
| Embed Go Core as a shared library through JNI | Could avoid one child process and allow in-process calls. | New ABI, Go runtime and callback lifecycle inside Android, crash coupling to the UI process, and a larger key-handling boundary. Does not by itself reduce P2P/PoW work. Defer unless measurements show executable boundaries are the bottleneck. |
| Embed selected Rust crypto/wallet code | Could reuse cryptographic primitives. | Core's chain, scanner, wallet orchestration, ring selection, and P2P are predominantly Go; a partial port risks protocol or wallet drift. The existing offline reader is a suitable narrowly scoped component. Defer a broader port. |

## Observed baseline and constraints

- On the affected everyday phone, **published preview.2** showed 7 h 18 m background use, 17 min CPU, roughly 543,000 packets, 4.1% for one daily window and 16% since full charge in another. These windows are not comparable, and the counters do not identify the traffic source. Obtain the detailed battery view and run a controlled baseline before promising savings. S22 sidecar measurements are not measurements of that phone.
- [`CoreService`](../app/src/main/java/com/blocknet/wallet/CoreService.java) owns a requested foreground sync session. Its 15-second monitor reconciles connectivity; transaction alerts poll every 15 seconds and announcements every 60 seconds. These schedules already existed in preview.2. Core's own `p2p/sync.go` loop checks every 30 seconds, while peer networking stays live. Merely changing Java poll intervals would leave that work running.
- [`NativeRuntime`](../app/src/main/java/com/blocknet/wallet/NativeRuntime.java) starts Core from the extracted native-library path, opens app-private storage under `getNoBackupFilesDir()/blocknet`, and stops the process with SIGTERM, waiting up to 20 seconds before forcing it. Core shutdown saves a loaded wallet, closes the chain and peers (`cli.go:280-302`, `daemon.go:588-615`); startup opens and verifies the chain, using checkpoints when available (`daemon.go:271-364`). Independently of checkpoint-accelerated verification, `NewChainWithCacheCap` eagerly rebuilds the canonical ring-member index from every stored block and output (`block.go:1208-1237,1328-1338,2146-2185`). Repeated stop/start can therefore incur full-chain reads and allocation without rerunning PoW on every stored block. A five-minute stop/start cycle may be expensive. **Measure it; do not assume it saves energy.**
- Core has no current cheap, restartable pause API. `p2p.Node.Stop` cancels its context and closes its libp2p host (`p2p/node.go:323-339`), so calling it as a temporary pause is not sufficient. A mobile suspend must be explicitly restartable and must account for in-flight sync, scanner writes, API requests, and peer streams.
- Android [periodic WorkManager jobs](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest) have a 15-minute minimum and can be delayed by Doze. Android also [restricts background foreground-service starts](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start). Do not promise exact five-minute wakeups, chain jobs together to evade that limit, request exact alarms, or ask users to disable battery protections. Immediate user-driven foreground catch-up is separate from best-effort background scheduling.
- The current Android build sets `seed: true` to tolerate unavailable bootstrap seeds while keeping the local API usable offline (`NativeRuntime.start`). Core also uses seed mode for a peer-ID endpoint (`daemon.go:570-575`). A mobile client must separate offline-start tolerance from network seed/serving behavior.

## Mobile behavior contract

1. **Offline and locked:** Local wallet authentication and the encrypted saved view continue independently of network permission and Core activity. Preserve [`OfflineSnapshotStore`](../app/src/main/java/com/blocknet/wallet/OfflineSnapshotStore.java), [`OfflineWalletReader`](../app/src/main/java/com/blocknet/wallet/OfflineWalletReader.java), wallet-file binding, lock-on-background, and cache timestamp labeling. A first run without a cache shows an honest empty/stopped state. No cached balance is presented as current; no offline send or broadcast is enabled.
2. **Active foreground sync:** On an allowed, validated connection, resume promptly when the wallet becomes foreground or the user explicitly requests sync. Keep the API on loopback, the cookie private, and wallet lock state unchanged. Do not add an app-kept password or auto-unlock. Refresh chain and wallet scan before treating balances as current. [`WalletRepository.send`](../app/src/main/java/com/blocknet/wallet/WalletRepository.java) must continue rejecting sends until sync and wallet scan are current and its existing review/idempotency guards pass.
3. **Background idle:** The candidate defaults to foreground-only graceful stop/restart when the mobile preference is absent; an explicit continuous-sync choice remains available. A true suspended Core would need to stop P2P, scanner, announcement polling, and checkpoint downloads, rather than just dim the UI or delay Java timers. A persisted notification must not say “running” while stopped. A manual **Stop sync** remains definitive. Android may kill a resident suspended process at any time; resume must detect process loss, restart from durable chain/wallet state, then recheck API lock and catch-up before showing current funds or allowing sends. Core's present API lock only changes a permission flag (`api_handlers.go:1655-1668`); a loaded wallet can retain keys and a cloned password in memory (`wallet/wallet.go:371-378,550-563`). Never describe suspend as clearing secrets; separately assess unloading the wallet on suspend and its effect on background scanning. The current fallback stops Core, losing background payment alerts and paying full startup cost on return; measure that cost before release.
4. **Best-effort background refresh:** Treat “about five minutes” as a research target, not a scheduling guarantee. First measure whether a restartable Core pause is cheaper than stop/start. If a user-selectable scheduled catch-up mode is justified, use Android-supported inexact jobs and constraints, accept deferral in Doze, and do not start a foreground service from an unqualified background callback. A 15-minute-or-longer periodic cadence may be the practical system-managed choice. Foreground opening always triggers an immediate catch-up attempt independent of that cadence.
5. **Network handover:** Wi-Fi-only mode immediately suspends network work on Wi-Fi-to-cellular transition and never starts downloads on cellular. Reconnect on permitted validated Wi-Fi. Use the already established [`SyncNetworkPolicy`](../app/src/main/java/com/blocknet/wallet/SyncNetworkPolicy.java) and bind every app-initiated HTTPS request to its permitted `Network`. Suspend/resume must be idempotent across rapid callbacks, process death, screen off/on, and service restarts.
6. **No mining; minimize serving:** Mobile configuration must keep mining disabled and reject any path that starts it. Avoid a publicly listening mobile node if protocol tests permit it; explicitly test no-listen, NAT traversal and hole-punch behavior. Setting a loopback or empty listen address is **not** sufficient for client-only behavior: Core registers PEX, block, transaction, Dandelion, and sync stream handlers on its libp2p host (`p2p/node.go:250-262`). `p2p/sync.go:225-250` answers GetHeaders/GetBlocks/GetBlocksByHeight/GetMempool, and `p2p/pex.go:602-631` answers GetPeers over connections the phone initiated. Gate those request handlers, seed peer-ID service, and any unnecessary announcement/relay response on **both inbound and outbound-originated connections**. Preserve `SyncMsgStatus` request/response and `SyncMsgNewBlock` ingress (`p2p/sync.go:225-278,597-630`), plus parsing responses to phone-initiated PEX requests; blanket sync or PEX stream rejection would break catch-up. Retain the minimum behavior required to discover peers, receive valid blocks, and broadcast privately; prove interoperability and avoid claiming zero serving until packet/handler tests confirm it. Do not weaken chain verification or discard Dandelion++ solely to reduce traffic.
7. **Privacy:** Private spend/view keys, seed, password, wallet files, and locally selected ring members remain on device. A remote-server balance or signing shortcut is outside this plan. A mobile patch may reduce peer count after measurement, but any loss of eclipse resistance, reorg detection, transaction propagation, or wallet privacy is a release blocker.

## Patch and repository boundaries

Add a versioned, reviewable mobile patch under `android/core-patches/`, applied **after** existing `0001-locked-wallet-activity.patch`, `0002-android-cgo-link-flags.patch`, and `0003-onchain-announcement-scan.patch` to the same pinned Core archive. Split lifecycle and peer-policy patches if independent review is clearer. Keep upstream Core checkout unmodified; treat each patch as source code with host tests. No wallet format, consensus rule, PoW algorithm, checkpoint trust, or signing primitive changes.

The lifecycle patch should add an authenticated, loopback-only mobile capability/version and suspend/resume/status API (or an equivalent local control channel). Define a state machine—`RUNNING`, `SUSPENDING`, `SUSPENDED`, `RESUMING`, `FAILED`—with serialized transitions, bounded cancellation and completion, generation IDs, and status reporting. Freeze new network and scan work before closing sockets; drain or cancel in-flight work without truncating chain or wallet files. Preserve API lock and cookie behavior, and state explicitly whether a loaded wallet remains resident with secret material. On resume, detect a lost process and reload durable chain/wallet state without bypassing validation; recheck API lock, wallet scan, and current chain status. If the libp2p host cannot be restarted safely, report that limit and use the measured foreground-only fallback. Never implement pause with SIGSTOP/SIGCONT.

The peer-policy patch should separate `allow_offline_start` from seed service, explicitly disable listening, NAT/hole punch, and the peer-ID endpoint in mobile mode, and enforce client-only handler behavior per connection and stream. Test inbound, outbound, and reconnected peers; specifically have a remote peer request blocks over a connection the mobile node initiated and assert refusal, while `SyncMsgStatus` round trips and `SyncMsgNewBlock` ingress still work. Preserve parsing of phone-initiated PEX replies while refusing remote GetPeers; verify mobile fetch and Dandelion++ broadcast. Keep desktop defaults unchanged and reject unknown mobile options. Mainnet and testnet remain separately scoped.

App integration belongs in `CoreService`, `NativeRuntime`, `WalletRepository`, and small lifecycle policy tests. Reconcile app foreground/background, lock, user-requested sync, and permitted connectivity through one owner/generation so a stale callback cannot restart Core after Stop sync or a Wi-Fi-to-cellular handover. Keep existing preview.3 address-book and localization work intact. Do not copy keys into Android preferences to implement the policy.

## Reproducible build and CI design

1. Keep the Core pin at `5a37ed52f0426951eaac2f0ae86bf0bb6d70a83e` until an independently reviewed Core upgrade. CI fetches that exact commit from `https://github.com/blocknetprivacy/core.git`, checks out detached, verifies `git rev-parse HEAD`, and builds from `git archive`; it must not follow a branch tip. Record source repository, commit, patch order and SHA-256, resolved `Cargo.lock`, Go and Rust versions, NDK revision/API, build flags, and output hash in provenance. Existing baseline patch hashes are recorded by [`build-core-android.sh`](../scripts/build-core-android.sh); add mobile patch hashes and a capability/version to that record.
2. Extend the current script and [CI workflow](../../.github/workflows/android.yml) rather than adding an unverified binary download. Current CI pins Go **1.26.5**, Rust **1.89.0**, NDK **30.0.16248370**, Android API **24** for the ARM64 executable, Android SDK **36**, and Java **17**. Keep locked Rust dependencies and readonly Go modules; capture resolved dependencies and hashes. Build the Rust static library for `aarch64-linux-android`, then the Go `GOOS=android GOARCH=arm64`, CGO-enabled PIE using NDK clang. Build in a fresh output directory; fail on a wrong Core commit or failed patch precheck. The current script archives the pinned commit and ignores uncommitted source changes rather than rejecting a dirty checkout; CI should use a fresh detached checkout, or add an explicit clean-tree check for local builds. Use cache only as an accelerator, never as source authority.
3. Core host tests cover wallet/lock, sync, peer handler policy, reorg, announcements, persistence, and send readiness. The script runs focused mobile regressions before cross-compilation; broader Core package tests passed on the final reviewed patch sequence. The isolated S22 sidecar passed dated offline viewing, foreground stop/restart, cache binding, and manual Stop persistence after app-scoped process death. No funded broadcast was used.
4. Every Gradle build now requires `-PcoreMobileDir=/absolute/provenance-checked/output`; [`verify-apk.py`](../scripts/verify-apk.py) requires the matching `--core-mobile-dir`. Both compare the packaged executable **byte for byte** with the selected output and verify source/patch/lockfile/provenance hashes. They reject a legacy Core or Mantle payload. CI uploads APK, source provenance, patch hashes, test reports, and SHA256SUMS.
5. Owner signing and publication use separate manual GitHub environment gates in [CI](../../.github/workflows/android.yml) and the [release procedure](CI_RELEASE.md). The release job rebuilds the same mobile Core from the pinned source.

## Migration and compatibility gates

- Preserve package ID `com.blocknet.wallet`, owner signing certificate, Android app-private paths, Core wallet filenames/format, network directories, and encrypted offline cache scope. Preview.2 must update **in place** only with a higher version code and the same owner certificate; debug signatures cannot replace it. Do not uninstall, clear data, reset wallets, rotate keys, or rewrite wallet files to test migration.
- Test an owner-signed upgrade with an independently backed-up **disposable** preview.2 wallet: locked launch, password and biometric path, cached view without connectivity, network transition, Core startup, scan, history, receive address, and unfunded send preview. Confirm loaded-wallet API lock remains effective, no private data leaks to logs/notifications, and backup export/import still works.
- If a Core patch needs persistent data changes, specify a versioned, reversible migration with an old APK read/rollback test **before** release. A forced stop must leave wallet and chain files intact. If rollback cannot read new data, block release and document a backup/restore path. Keep the existing recovery warning; do not use a production wallet as the test fixture.

## Measurement and acceptance sequence

1. **Baseline first:** On the affected preview.2 phone, collect the battery-detail time window, app/version, foreground/background time, permitted network, sync height/peer count, and whether the screen was locked. With consent and no wallet contents, collect UID-scoped CPU, network bytes/packets, service duration, wakeups, and battery estimates in comparable unplugged runs. Repeat under the same Wi-Fi/signal, charge range, chain lag, and screen state. The reported 4.1% and 16% refer to different windows and cannot be converted to an hourly rate. Record measurement uncertainty; set a numerical power target only after baseline variance is known.
2. **Prototype on a disposable test profile:** Measure cold start, warm resume, suspend completion, chain verification time, ring-index rebuild time and peak RSS, wallet scan catch-up, P2P connections, and packets for continuous, foreground-only stop/start, and true Core suspend. Compare whole-device/UID energy over matched windows. Reject a five-minute restart cycle if repeated indexing, verification, peer bootstrap, or wallet save outweighs idle savings. Consider a persistent ring index only as a separately reviewed, integrity-checked Core optimization. Do not weaken validation to make a battery target.
3. **Functional acceptance:** Locked/background suspend produces no ongoing Core sync, scanner or peer traffic; user Stop sync prevents resurrection; allowed Wi-Fi resumes; cellular restriction never permits network calls; cold offline launch opens only an authenticated stale view or an honest no-cache state; foreground launch begins catch-up immediately; sends remain blocked until sync, scan, fee/ring selection, and review guards succeed. Test rapid Wi-Fi/cellular handovers, Doze deferral, screen lock/unlock, process death, reorg, chain repair, and mainnet/testnet scope.
4. **Protocol acceptance:** Confirm valid block/transaction reception, reorg handling, checkpoint validation and PoW outside trusted checkpoint ranges, local output scan, local sign and ring selection, Dandelion++ broadcast, and no mining. Verify peer stream handling on both inbound and phone-initiated connections. A no-listener claim requires socket evidence; a no-serving claim requires handler and packet evidence.
5. **Release:** Run host unit tests, Android unit/lint/APK checks, disposable ARM64 integration, then physical-device battery and migration tests. Review the exact CI artifact hashes and owner-signed candidate separately. Publish only after measured improvement, privacy/security parity, and explicit owner approval.

## Open decisions after measurement

Decide whether to release the prepared foreground-only default after measuring battery improvement against delayed incoming alerts and catch-up latency on a synced device. Decide whether a best-effort periodic background check adds value; Android cannot guarantee a five-minute cadence. Decide whether strict client-only peer behavior is protocol-compatible after interoperability tests. None of these decisions should change the existing offline unlock or signing model.
