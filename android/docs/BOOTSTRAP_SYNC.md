# Initial wallet sync in the mobile candidate

The foreground-only Core option now has a narrow first-sync exception. A newly created, restored, imported, or previously unmarked local wallet keeps the already requested foreground service running after the screen turns off while connectivity is permitted. Manual **Stop sync** and the Wi-Fi-only preference still stop network work. Background status reads are authenticated; signing, sending, and an unlocked wallet UI still require the visible app.

Core reports a recent successful cumulative-work comparison with a connected peer and the wallet scanner's exact canonical chain tip/hash. With foreground-only mode enabled and the wallet in the background, Android stops Core after readiness, then commits completion only when a private nonce-bound shutdown receipt confirms a successful wallet save and the same wallet and canonical tip. A crash, failed save, forced stop, changed tip, or missing receipt leaves the wallet pending. The record is scoped by network and wallet filename; create, restore, and import clear it before changing the wallet. With foreground-only mode disabled, Core keeps running and does not enter this auto-stop path.

Android can kill the process while the screen is off. The service is not restarted in the background after that. This feature does not persist a new wallet password; the existing optional biometric vault has its own Keystore-encrypted password storage. API lock alone leaves loaded wallet keys and a cloned password in the resident Core process. Opening and unlocking the wallet resumes its saved scan. If Core restarts without a loaded wallet, a dismissible notification asks the user to open the wallet to resume initial sync; it does not assert that the final chain tip was saved. Cached balances remain dated and cannot be used as a current balance or to send offline.

The local candidate adds a CPU-only partial wake lock while a requested first sync remains pending, the screen is off, and the selected connection is permitted. Each system lease lasts at most two minutes. The service continues acquiring short leases while Core's authenticated private bootstrap result shows a higher validated canonical chain height or a higher scanned wallet height for the same selected wallet. The first result only sets a baseline. A completed foreground wallet switch resets that scope after the service confirms ownership of the new Core generation; Core's later progress must match the wallet identity derived from the successful load response. If ownership reconciliation is still queued, the old wallet's cutoff is deferred to a fixed two-minute monotonic deadline with no CPU wake lock. This handoff never renews from callbacks or another pending event; when Android next runs the service after expiry, Core is stopped. Callbacks, peer count, unchanged results, and reconnects do not count as progress. After 15 minutes without measured advancement while the wallet app is backgrounded, Core is stopped and a notification asks the user to reopen the wallet to continue. The same stall cutoff applies when another app keeps the screen on, though no CPU wake lock is held then. Screen wake releases the lock; completion, connectivity loss, Stop, error, or service teardown release it immediately. The saved Start sync choice remains intact, so a visible reopen may start a new session. An unloaded wallet cannot supply scan progress and is subject to the same stall cutoff until reopened. This is a bounded battery tradeoff, not proof of background progress through Doze, process death, or a peerless network. Device checks still need a disposable wallet and peer on Wi-Fi: screen off during chain download and wallet scan, Wi-Fi to cellular with mobile data disallowed, reconnect, manual Stop, wallet switch, another app remaining interactive, process kill/reopen, a sync lasting over 15 minutes with real progress, a 15-minute stall, and a complete scan followed by background pause. Measure battery use and restart cost before claiming savings.

The package-bound disposable screen-off acceptance phase and its strict fixture prerequisites are documented in [BOOTSTRAP_SCREEN_OFF_QA.md](BOOTSTRAP_SCREEN_OFF_QA.md). The first S22 run of the wake-lock candidate reached chain height 2 off-screen but left its fresh wallet at scan height 0, so it failed. Host reproduction found that Core accepted fetched sync blocks without notifying the wallet scanner. Patch 0011 moves that notification to the accepted-block path and has host regression coverage; the rebuilt candidate still needs physical screen-off acceptance before this feature can be called working.
